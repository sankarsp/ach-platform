# ISO 20022 channel

Corporate clients can send ACH instructions as ISO 20022 XML instead of JSON or Nacha files. Every transaction becomes an ACH entry through the same pipeline as the REST API (rules catalog, window planning, sanctions, fraud, AML, limits). Nothing sent in ISO 20022 bypasses a control.

| Message | Direction | Endpoint |
| --- | --- | --- |
| pain.001 (credit transfer initiation, tested with .001.09) | Client → bank | `POST /v1/iso20022/pain.001` |
| pain.008 (direct debit initiation, tested with .001.08) | Client → bank | `POST /v1/iso20022/pain.008` |
| pain.002.001.10 (payment status report) | Bank → client | Returned on intake; `GET /v1/iso20022/messages/{id}/pain.002` for the live status |
| camt.054.001.08 (debit/credit notification) | Bank → client | `GET /v1/iso20022/camt.054?originator_id=&day=` |
| camt.053.001.08 (account statement) | Bank → client | `GET /v1/iso20022/camt.053?originator_id=&day=` |

Send the XML as the request body with `Content-Type: application/xml`, or as JSON `{"content": "<xml>"}`. Samples for the sandbox originators: `GET /v1/iso20022/samples`.

## How pain fields map to ACH

| ISO 20022 element | ACH result |
| --- | --- |
| `PmtTpInf/LclInstrm` (Cd or Prtry) = PPD, CCD, CTX, WEB, TEL or IAT | That SEC code (explicit choice wins) |
| Creditor/debtor country outside the US | IAT, with the 7 mandatory addenda built from the party and agent data |
| Counterparty identified as an organisation (`Id/OrgId`) or business category purpose | CCD, or CTX when remittance is structured or runs to several lines |
| Otherwise | PPD |
| `CtgyPurp/Cd` SALA, PENS, SUPP, TAXS, LOAN, INTC… | Purpose and company entry description (SALA → PAYROLL, so the 2026 standard description is applied) |
| `SvcLvl/Cd` = SDVA | Same Day ACH requested (still subject to eligibility and the per-entry limit) |
| `ReqdExctnDt` / `ReqdColltnDt` | Effective entry date; weekends and Fed holidays move it to the next banking day |
| `RmtInf/Strd` | CTX addenda as EDI `RMR*IV*<invoice>*PI*<amount>\` segments |
| `RmtInf/Ustrd` | Addenda text (one 80-character record for PPD/CCD/WEB; up to two 717 records for IAT) |
| `CdtrAgt` / `DbtrAgt` `ClrSysMmbId/MmbId` | ABA routing number (required for domestic entries) |
| `CdtrAcct/Tp/Cd` = SVGS | Savings transaction codes (32/37) |
| `DrctDbtTx/MndtRltdInf` MndtId + DtOfSgntr | Required for pain.008; stored with the payment as authorization evidence |
| `PmtId/EndToEndId`, `InstrId`, `UETR` | Kept on the payment and echoed in pain.002 and camt.054 |

The originator is the caller's own originator for originator API keys. For operators it is identified from `InitgPty`, the debtor/creditor `Id` (the 10-character Nacha company ID) or the settlement account. A debtor account (pain.001) or creditor account (pain.008) that isn't the originator's settlement account is rejected (AC02 / AC03).

## Status codes in pain.002

| Payment state | TxSts | Reason |
| --- | --- | --- |
| Rejected at intake | RJCT | ISO code for the validation failure, e.g. RC01 bad routing, AM02 over limit, AG03 SEC not allowed, MD01 no mandate, AM05 duplicate EndToEndId, AM03 non-USD |
| Held for review | PDNG | NARR with the hold reason |
| Queued for a window | ACCP | |
| Sent to FedACH | ACSP | |
| Settled | ACSC | |
| Returned | RJCT | Nacha code mapped to ISO (R01 → AM04, R02 → AC04, R03/R04 → AC01, R16 → AC06, R05/R07/R10/R29 → MD01…); the Nacha code is always in AddtlInf |
| Cancelled | CANC | |

Group status is RJCT when every transaction is rejected, PART when some are, otherwise the common accepted state. Whole-message failures: wrong NbOfTxs (AM18), CtrlSum mismatch (AM16), reused MsgId (HTTP 409, DU01).

## Cash reports

- **camt.054** lists, for one originator and booking day, every settled entry (ACH credit `PMNT/ICDT/ACDT`, ACH debit `PMNT/IDDT/PMDD`) and every return (`ARET`, reversal indicator, `RtrInf` with ISO and Nacha reasons). Notifications of Change are summarised in `AddtlNtfctnInf`.
- **camt.053** is the end-of-day statement of the originator's settlement account at the bank: opening and closing booked balances, totals, and one entry per core posting linked back to the payment and its EndToEndId.

## Security and limits

XML is parsed with `defusedxml` (no DTDs, entity expansion or external references) and capped at 20 MB. Validation is structural and business-rule based; the official ISO 20022 XSDs could not be downloaded in the build environment, so adding XSD validation (for example with `lxml` and the published schemas) is recommended before production.
